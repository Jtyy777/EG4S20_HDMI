> 这份台账只管**功耗**，性能迭代仍在 `doc/perf_log.md`。一个文件一件事。

| 查的地方 | 结果 |
|---|---|

| `td.exe` 字符串 + `doc/gui/helpmenu.json` | 无功耗分析菜单 |

数据手册 `EG4S20_DataSheet_V1.4.pdf` 也没有功耗估算章节，只有一句"静态功耗低至 5mA"。
（手册末尾注释指向 `Eagle_DataSheet_v1.9.pdf`，各电源域电流表若存在只在那一版。）

所以 mW 只能自己算 + 自己测。下面三层，缺一层结论就站不住。

## 1. 三层量化框架

动态功耗只有四个自变量，其中两个在整个芯片内是常数：

```
P_dyn = Σ  C · V² · f · α · N
         ↑   ↑   ↑   ↑   ↑
         |   |   |   |   └─ 参与翻转的触发器/节点数  ← 能改（门控、削逻辑）
         |   |   |   └───── 翻转率 0~1                ← 能改（使能、数据编码）
         |   |   └───────── 频率                      ← 能改（降频）
         |   └───────────── 核压 1.2V（固定，EG4S20 VCCINT）
         └───────────────── 每节点电容（固定，工艺决定）
```

C 和 V 测不到也改不了，所以不追绝对值，改追**比例**。

### 第一层：翻转预算（前向估算，改之前就知道能省多少）

度量单位 `B = Σ N × f`，量纲 FF·MHz。工具：`doc/power/budget.py`。

```bash
python doc/power/budget.py            # 基线表
python doc/power/budget.py --scenario # 加上候选措施的 Δ
```

数据全部来自 TD 自己生成的报告，每次 P&R 自动刷新，不依赖手抄：

- `phy_1/info_signage_v1.0_phy.area` —— 每个实例的 `seq`（触发器数），有层级缩进
- `phy_1/final_timing.rpt` —— Clock Summary 的各域频率；End Point 行反查实例所属时钟域

**它是上界**（隐含 α = 1），不能当 mW 报。用途只有两个：排优先级、算比例。

### 第二层：实测翻转率 α（把上界收成估算值）

寄存器有使能时不是每拍都翻，α 可能只有 0.1~0.3。三条路，按成本从低到高：

1. **代码核对**：看模块在空闲时是否还有计数器在跑。粗但快。
2. **ModelSim 统计**：跑 `$dumpvars`，脚本统计每拍翻转的寄存器数。准，但要跑够长的时间窗才有代表性。
3. **板上 A/B**：见第三层。

### 第三层：板上实测（唯一的真值）

见第 4 节协议。**答辩时只有这一层的数字能当"实测功耗"讲**，前两层只能叫"估算/上界"。

## 2. 基线（2026-11-01，`phy_1` 15:33 那次，含 param_cdc）

```
=== 按时钟域的翻转预算（基线） ===
时钟域             f/MHz   触发器    B=FF·MHz    占比
sd_card_clk      100.000    2675     267500    63.8%
ext_mem_clk      125.000     562      70250    16.8%
video_clk         25.000    2693      67325    16.1%
clk                50.000     170       8500     2.0%
hdmi_5x_clk       125.000      36       4500     1.1%
audio_mclk         12.295      75        922     0.2%
合计                        6261     418997
```

资源基线：LUT 11319 / 19600，REG 6426，BRAM 27 / 64，DSP 11 / 29，PLL 3 / 4。

**结论一：重心不在视频通路。** `sd_card_clk` 100MHz 一个域占了 63.8%，
单是 `sd_card_bmp_m0` 一个实例就 60.5%（2543 个触发器挂在 100MHz 上）。
视频通路（video_clk 25MHz）只占 16.1%——它频率低，寄存器多也没那么烧。

**结论二：`img_scaler` 是单点最大户。** 798 个触发器 × 100MHz，
占全设计 19.0%，而它只在读卡加载图片时才有活干。

### 3.1 P-1 为什么被否决（2026-11-01 核算）

原本的理由是「50MHz 下 SDRAM 带宽仍然够」，但漏了一条硬绑定：

```
spi_master：DCLK 半周期 = (clk_div + 2) 个 sys_clk，clk_div = 0 已是最快档
             → DCLK = sys_clk / 4
             → 100MHz 出 25MHz；50MHz 只能出 12.5MHz
```

`clk_div` 是 16 位无符号，最小就是 0，**没有负档可以补**。所以 `sd_card_clk` 降半，SD 卡读速直接减半：

| 素材 | 扇区 | 100MHz 理论 | 50MHz 理论 | 50MHz 实测估 | 能否藏在 3s dwell 内 |
|---|---|---|---|---|---|
| 640×480 | 1801 | 0.30s | 0.59s | 0.80s | 能 |
| 1024×768 | 4616 | 0.76s | 1.51s | 2.04s | 能 |
| 1440×1080 | 9113 | 1.49s | 2.99s | **4.03s** | **不能** |
| 1920×1080 | 12440 | 2.04s | 4.08s | **5.50s** | **不能** |

用户素材正是 1440×1080。三缓冲的「后台预读」只有在「读得比 dwell 快」时才藏得住；一旦读得比 dwell 慢，观感就退化成「切过去先看白屏，等卡读完」——正是之前那个「第 4 张转第 1 张加载失败」现象的根子，只是这次不会报失败、而是一直等。

另外三个连带影响，改之前必须一起处理：

- `CLK_FREQ_HZ` 参数（`100_000_000`）不同步改，`switch_latency` 的 10ms 时基会把切换耗时显示成两倍；
- 兜底超时 `800_000_000` 拍在 50MHz 下等于 **16s** 而非 8s，语义变了（虽然不会误触发）；
- `img_scaler` 的生成速率从 33.3 降到 16.65 Mpixel/s，低于 480p60 的 18.41 —— 静态图不受影响，但将来要做视频流这条路就断了。

写侧吞吐本身**不是**问题：跨域 FIFO 512 深、读侧排水 115.9 字/us，写侧最坏 50 字/us，净排水为正；一帧 18.45ms 也远小于 8s 超时。所以否决的原因纯粹是 SPI，不是 FIFO。

完整核算见 `doc/power/throughput.py`。

### 3.2 替代路线（P-1 的替补）

| # | 措施 | ΔB | 难度 | 说明 |
|---|---|---|---|---|
| P-1a | `img_scaler` 单独拆到 50MHz 域 | 约 −9.5% | 高 | 输入侧是准静态数据流（1 像素/32 拍），可逐像素握手跨域；输出侧必须加异步 FIFO。**不动 SPI**，所以读卡时间不变 |
| P-1b | `ext_mem_clk` 125 → 62.5MHz | −8.4% | 中 | 就是 P-3，改 PLL + 重配 SDRAM IP；带宽已核算够（需求 78MB/s，供给有效 150MB/s） |
| P-1c | `img_scaler` 加 idle CE | −19.0%（上界） | 低 | 就是 P-2，只改 RTL，不改时钟 |

按「收益/风险」排，先做 P-1c，再考虑 P-1b，P-1a 最后。

### 3.3 P-1c（即 P-2）实施记录：行缓冲读使能

改的东西只有一处 —— `img_scaler.v` 里三条行缓冲的读。

**改之前**：读是无条件的，`q0/q1/q2` 每拍都更新：

```verilog
always @(posedge clk) begin
    q0 <= line0[rd_addr];
    q1 <= line1[rd_addr];
    q2 <= line2[rd_addr];
end
```

一帧 1440×1080 的加载里，填充侧跟 SPI 走占 3%，生成侧输出 307200 像素占 0.6%，**剩下 96% 两个状态机都停在原地**。寄存器停着不动、D 端等于 Q，本来就不翻转；但三条行缓冲（共 9 块 BRAM）仍在每拍读 —— 地址不变、数据不变，wordline 和读出放大器却照常工作。这是空转期间唯一还在耗电的地方。

**改之后**：加一个由生成侧状态译码出来的使能，只有真要数据的三个状态才读。

```verilog
assign ram_rd_en = (gstate == G_RD) || (gstate == G_CALC) || (gstate == G_OUT);
```

三个状态缺一不可，理由写在代码注释里：`G_RD` 少了会让整行第 0 列拿到上一行最后一列（这个坑之前踩过），`G_OUT` 要整状态包住（地址第 0 拍给、RAM 第 1 拍出、第 2 拍采）。

**收益必须说准确**，否则答辩会被问穿：

| 项 | 能否省 | 原因 |
|---|---|---|
| 9 块 BRAM 读端口空转 | ✅ 这是本刀的全部 | 96% 空闲期一直在读 |
| 798 个触发器的 D 端翻转 | ❌ 本来就不翻 | 状态机停着，D = Q |
| 798 个触发器的时钟树 | ❌ CE 管不到 | CE 只挡 D 端，不挡时钟；要省得上 clock gating，TD 6.2.1 没找到对应原语 |

所以原先 `budget.py` 里那个 −19.0% 是 `B = N×f` 的上界（假设 α=1），真实 α 约 0.04，不能按 19% 报。实际量级是「几毫瓦」，只能上板测出来。

**验证结果（2026-11-01）**：

- 功能等价：新旧两版 RTL 用同一套参数跑 9 组，输出逐字节一致
  （直通 32×24 / 缩小 32×24←64×48 / 32×24←40×30 / 放大 72×54←32×24 / 非整数 33×25←100×76 /
   宽受限 64×24←128×24 / 高受限 64×48←64×120 / 1080p 比例 64×48←144×108 / 64×48←160×120）
- 使能有效：p1080 配置在 0.5~3.0ms 六个采样点全部 `gstate=G_IDLE`、`ram_rd_en=0`
- 回归环境留在 `.workbuddy/sim/img_scaler/`，对照版本 `abtest/img_scaler_before.v`，输出 `out_new_*.txt` / `out_old_*.txt`

**P-1c 已回滚（2026-11-01 16:50）**：上板后画面出不来，用户要求回滚。`rtl/img_scaler.v` 已还原到
改动前状态（与 `.workbuddy/sim/img_scaler/abtest/img_scaler_before.v` 逐行比对一致，`ram_rd_en`
残留 0 处，816 行）。带 P-1c 的版本备份在 `.workbuddy/tmp/img_scaler_with_p1c.v`，需要时可再取回。
本轮 P&R 本身是成功的（bit 16:46:23 生成，WNS −6.699，日志 0 ERROR），所以回滚是为了**隔离功能问题**，
不是流程问题。下面这段资源核查结论仍然有效——它只说明「TD 会把读使能落成 BRAM 原生 CE」，
不代表功能在板上一定正常，仿真覆盖不到 BRAM 端口映射的时序细节。

**综合/布局核查（2026-11-01 16:44，phy_1 的 place 阶段报告）**：

| 项 | 基线（P-1c 之前） | 本次 | 差值 |
|---|---|---|---|
| `u_img_scaler` bram | 9 | 9 | 0 ✅ |
| `u_img_scaler` lut | 1264 | 1266 | +2 ✅ |
| `u_img_scaler` seq | 798 | 783 | −15 |
| `u_img_scaler` le | 1565 | 1570 | +5 |
| 整片 lut / reg / bram / dsp | 11437 / 6287 / 27 / 11 | 11222 / 6425 / 27 / 11 | — |

（整片那一行的基线取自更早一份 phy 报告，跨了多轮改动，只能看量级，不能当本轮差值；判 P-1c 只看 `u_img_scaler` 那四行。）

结论：**读使能确实落在了 BRAM 的原生 CE 上**。如果是落到触发器上，`lut` 应涨约 3×24=72，
`bram` 也可能因端口结构变化而增减；实测 bram 不变、lut 只差 2（工具噪声级），说明 TD
把 `if (ram_rd_en)` 直接映射成 BRAM 的读使能。

复现命令：

```
python doc/power/check_area.py            # 读 phy_1 的报告并与 area_baseline.json 比对
python doc/power/check_area.py --save     # 同时把报告归档到 doc/timing_rpt/
```

脚本存在的原因：TD 每次重跑 P&R 都会覆盖 `phy_1/*.area`，基线就是这么丢过一次的。
`--save` 必须在当次跑完立刻执行。

## 4. 测量协议

### 4.1 器材

- 0.1Ω 1% 采样电阻（串在 5V 输入）
- 4.5 位以上万用表（测采样电阻压降，比串联测电流对回路影响小）
- 或可编程电源直接读电流，分辨率 0.1mA
- 示波器（抓切图瞬间的峰值电流，可选）

### 4.2 控制变量（缺一项，数字就没有可比性）

- 同一块板、同一室温，开机预热 ≥5 分钟再测
- 同一张 BMP、同一个显示状态（停在某一张图上，不要停留在切图瞬间）
- 数码管显示内容固定
- SD 卡不插拔，卡内文件不变
- 每次改完重新 P&R + 下载，**不要用 JTAG 热加载的旧配置混测**

### 4.3 两个必测的基准点

| 基准点 | 怎么造 | 用途 |
|---|---|---|
| `I_idle` | 烧一个空工程（只有时钟 + 一个计数器点灯） | 板的底噪：DCDC 空载 + SDRAM 待机 + LED |
| `I_base` | 当前工程正常显示 | `I_base − I_idle` 就是本设计给 FPGA 侧加的电流 |

有了这两个点，之后每项措施测到的 `ΔI` 才有参照：
**`ΔI / (I_base − I_idle)` 应该和第一层算出的 `ΔB / B_total` 大致同量级**。
两者差太多，说明该措施的 α 假设是错的——这就是交叉验证。

### 4.4 单次测量

1. 稳定 60s，读 3 次（间隔 20s），取中值
2. 记到台账，注明改动、资源、翻转预算
3. 有疑问就重烧一遍再测，别在同一份 bit 上反复读

## 6. 局限（写在前面，别让评委问出来）

1. **B 是上界**，隐含 α = 1。真实动态功耗可能只有它的 1/3~1/2。
2. **算不出绝对 mW**，因为缺 C（每节点电容）。想要绝对值只能靠第 4 节的标定。
3. **IO 功耗不在 B 里**。HDMI TMDS 差分对、SDRAM 32 位总线、数码管驱动的电流由外部负载决定，
   板级实测包含它们，模型不含。所以 P-4 这类纯 IO 措施，模型给不出可信数字。
4. **5V 输入电流包含 DCDC 损耗**。所以实测的 ΔI×5V 是"系统级"节省，比芯片级数字大，
   但答辩讲系统功耗反而更实在——说清楚是哪一级就行。
